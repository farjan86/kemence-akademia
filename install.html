1. Adatbázis (Supabase) — ITT KEZDŐDIK

1.1 — Supabase projekt

Hozz létre egy Supabase projektet (élesben az ügyfél fiókjában). EU régió ajánlott.

1.2 — db/01-schema.sql lefuttatása (a VÁZ)

Supabase → SQL Editor → másold be és futtasd le a db/01-schema.sql teljes tartalmát. Ezzel indul minden. Ez létrehozza:

  • a foglalás-táblákat: workshops, bookings, settings, email_sablonok, email_log;
  • az Egyedi programok + Ajánlatok ág tábláit: egyedi_programok, ajanlatok, ajanlat_log, ajanlat_sablonok (+ 5 ajánlat-sablon);
  • a biztonságot (RLS-szabályok), a programok nézetet, a foglalt_helyek() függvényt;
  • a túlfoglalás-védelmi triggert (múltbéli publikus foglalást is tilt);
  • a 7 foglalási e-mail sablont és a beállítások alap-sorát.
Az automatikus visszaigazoló trigger és a napi emlékeztető cron NINCS a 01-ben (projekt-specifikus értékek kellenek hozzá) — azok a 3. szakaszban jönnek.
Melyik fájl kell egy ÜRES projekthez? Csak a számozottak: 01–04.
  • m_ előtagúak (pl. m_09-foglalasi-korlatok.sql) = a fejlesztői adatbázis utólagos foltjai. Üres projekten NE futtasd őket — a 01-schema.sql már mindent tartalmaz, amit hozzáadtak.
  • t_ előtagúak = technikai eszközök (demó-adat, üres állapot, Minup-import). Nem részei a telepítésnek, csak akkor futtatod, ha épp arra van szükség.

1.3 — Storage bucketek (KÉTTŐ)

Futtasd le a db/02-storage.sql-t — ez létrehoz két buckettet a szükséges jogosultságokkal:

  • program-fotok — PUBLIC (a program- és egyedi program-képek innen jelennek meg a főoldalon);
  • ajanlat-csatolmanyok — PRIVATE (az elfogadott ajánlatok csatolmányai; csak admin + a send-ajanlat-email éri el).

Ha az SQL jogosultsági hibát ad, hozd létre őket kézzel: Supabase → Storage → New bucket → program-fotok (Public), majd ajanlat-csatolmanyok (Private).

Írd bele a projekt Supabase URL-jét és az anon public kulcsot:

3. E-mail automatika (trigger + cron)

Ez NINCS a 01-ben (projekt-specifikus értékek kellenek). Előfeltétel: a 2. szakasz (deploy + secretek) kész.

A <PROJECT_REF> és <ANON_KEY> értéket a legegyszerűbb a web/js/config.js-ből kimásolni (már ki van töltve):
  • <PROJECT_REF> = a SUPABASE_URL-ben a https:// és a .supabase.co közötti rész.
  • <ANON_KEY> = a teljes SUPABASE_ANON_KEY érték.
Ez a szakasz (3.2, 3.3 és a teszt-lekérdezések) mind ezt a kettőt használja.

3.1 — Extensionök bekapcsolása

Supabase → Database → Extensions → keresd és kapcsold BE: pg_net (a trigger + cron http-hívásaihoz) és pg_cron (a napi ütemezéshez).

3.2 — Automatikus visszaigazoló + csapat-értesítő (trigger)

Foglaláskor magától kimegy a visszaigazoló (vendég) + csapat-értesítő (csapat cím). A Database Webhook felület helyett SQL-ből (megbízhatóbb). Az SQL Editorban futtasd le — előbb cseréld ki a két helykitöltőt:

create extension if not exists pg_net;

create or replace function public.trg_uj_foglalas_email()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  if new.statusz = 'jovahagyasra_var' then
    perform net.http_post(
      url     := 'https://<PROJECT_REF>.supabase.co/functions/v1/send-email',
      headers := jsonb_build_object(
                   'Content-Type', 'application/json',
                   'Authorization', 'Bearer <ANON_KEY>'
                 ),
      body    := jsonb_build_object('type', 'INSERT', 'record', to_jsonb(new))
    );
  end if;
  return new;
end; $$;

drop trigger if exists trg_uj_foglalas_email on public.bookings;
create trigger trg_uj_foglalas_email
after insert on public.bookings
for each row execute function public.trg_uj_foglalas_email();

(Ugyanez a fájl: db/03-auto-visszaigazolo-trigger.sql.) Kikapcsolás: drop trigger trg_uj_foglalas_email on public.bookings;

⚠️ Seed + trigger: ha a demó-seedet (db/t_seed-demo-foglalasok.sql) újrafuttatod aktív triggerrel, minden új foglalás küld egy levelet. Seed előtt kapcsold ki a triggert.

3.3 — Napi emlékeztető (cron)

Mit csinál: minden reggel megnézi, mely program van MÁSNAP, és a jóváhagyott foglalóknak kiküldi az emlékeztetőt.

Előfeltétel: létezzen az „emlékeztető" sablon (a db/01-schema.sql-ban benne van), és a pg_cron + pg_net legyen bekapcsolva (3.1).

Beállítás — az SQL Editorban futtasd le (cseréld ki a helykitöltőket):

create extension if not exists pg_cron;
create extension if not exists pg_net;

select cron.schedule('kemence-napi-emlekezteto', '0 8 * * *', $$
  select net.http_post(
    url     := 'https://<PROJECT_REF>.supabase.co/functions/v1/send-email',
    headers := jsonb_build_object('Content-Type','application/json',
                                  'Authorization','Bearer <ANON_KEY>'),
    body    := jsonb_build_object('booking_id', b.id, 'tipus', 'emlekezteto')
  )
  from public.bookings b join public.workshops w on w.id = b.workshop_id
  where b.statusz = 'jovahagyott'
    and (w.idopont at time zone 'Europe/Budapest')::date
        = ((now() at time zone 'Europe/Budapest')::date + 1)
$$);

(Ugyanez a fájl: db/04-emlekezteto-cron.sql. Napi 8:00 UTC. Ellenőrzés: select jobname, schedule, active from cron.job;)

Azonnali teszt (hogy ne kelljen a napi futásra várni) — pár jóváhagyott foglalónak rögtön küld emlékeztetőt (dátumszűrő nélkül):

select net.http_post(
  url     := 'https://<PROJECT_REF>.supabase.co/functions/v1/send-email',
  headers := jsonb_build_object('Content-Type','application/json',
                                'Authorization','Bearer <ANON_KEY>'),
  body    := jsonb_build_object('booking_id', b.id, 'tipus', 'emlekezteto')
)
from public.bookings b where b.statusz = 'jovahagyott' limit 3;
Fontos a különbség: az ütemezett cron (fent) MÁR tartalmazza a „másnap" dátumszűrőt — magától, naponta fut, és csak a következő napi program jóváhagyott foglalóinak küld. Nincs vele több teendő. Az „azonnali teszt" ezzel szemben egyszeri, dátumszűrő nélküli próba (nem ismétlődik). Ellenőrzés, hogy be van-e ütemezve: select jobname, schedule, active from cron.job;

3.4 — Ajánlat auto-visszaigazoló + csapat-értesítő (trigger)

Ugyanaz, mint a 3.2, csak az ajánlatkérésekre — a send-ajanlat-email függvényt hívja. A db/03-auto-visszaigazolo-trigger.sql immár EZT IS tartalmazza; futtasd le az SQL Editorban (ugyanaz a két helykitöltő, mint a 3.2-nél):

create or replace function public.trg_uj_ajanlat_email()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  if new.statusz = 'ajanlatra_var' then
    perform net.http_post(
      url     := 'https://<PROJECT_REF>.supabase.co/functions/v1/send-ajanlat-email',
      headers := jsonb_build_object('Content-Type','application/json',
                                    'Authorization','Bearer <ANON_KEY>'),
      body    := jsonb_build_object('type','INSERT','table','ajanlatok','record', to_jsonb(new))
    );
  end if;
  return new;
end; $$;

drop trigger if exists trg_uj_ajanlat_email on public.ajanlatok;
create trigger trg_uj_ajanlat_email
after insert on public.ajanlatok
for each row execute function public.trg_uj_ajanlat_email();

Előfeltétel: a send-ajanlat-email deployolva (2.4), a pg_net bekapcsolva (3.1). Kikapcsolás: drop trigger trg_uj_ajanlat_email on public.ajanlatok;

4. Hosting és élesítés (Hostinger)

A frontend statikus (nincs szerveroldali kód, nincs build), ezért bármelyik tárhely kiszolgálja. Élesben a Hostinger — az ügyfélnek úgyis van ott csomagja (a mobilkemence.xyz + webshop miatt), és a domain + DNS is ott van, így a kemence-akademia.xyz is oda kerül, egy helyre. Így a telepítés nem függ a fejlesztő GitHub- vagy Netlify-fiókjától sem — az oldal fájljai az ügyfél tárhelyén vannak. (A demó ettől külön, a Cloudflare-en fut — lásd 4.5.)

4.1 — Frontend fel a Hostingerre (éles)

  1. hPanel → Websites → Add website → kemence-akademia.xyz (a meglévő tárhely-csomagon belül, a többi oldal mellé). Ez létrehoz egy webgyökér-mappát (pl. .../kemence-akademia.xyz/public_html). (Ha a domain már ott van egy régi oldallal, ez a lépés kimarad — lásd 4.2.)
  2. ELŐBB a config.js: a web/js/config.js-ben az éles Supabase projekt URL-je + anon kulcsa legyen (nem a fejlesztőié). Ezt még a csomagolás előtt írd át.
  3. Fájlfeltöltés: a web/ mappa TARTALMÁT (nem magát a web mappát) töltsd fel a webgyökérbe. Így az index.html a gyökérbe kerül, az admin a /admin/-ra. Három mód (lásd alább).
  4. A web/.htaccess is menjen fel (átirányítások, gyorsítótár, mappalistázás tiltása). A fájlkezelőben kapcsold be a rejtett fájlok megjelenítését, hogy lásd.
  5. SSL (HTTPS): hPanel-ben kapcsold be az ingyenes SSL-t (Let's Encrypt) a domainre, és a Force HTTPS kapcsolót.
  6. www átirányítás: állítsd be, hogy a www.kemence-akademia.xyz a fő címre menjen (hPanel beépített opció).
Feltöltési módHogyanMikor ezt

A backend független a hostingtól: a Supabase, a Resend és a trigger/cron ugyanúgy megy, akárhol vannak a statikus fájlok — a böngésző a config.js alapján csatlakozik a Supabase-hez.

4.2 — A RÉGI oldal lecserélése (a domain már foglalt!)

A kemence-akademia.xyz címen már van egy működő oldal a Hostingeren: egy statikus HTML (nincs mögötte WordPress), egy főoldallal és három aloldallal. Nem kell átirányítás egy másik címre — ugyanazon a domainen cserélődik a tartalom. A DNS-hez, a domainhez, a tanúsítványhoz nem kell nyúlni.

  1. Mentsd le a régit. Töltsd le a public_html tartalmát a gépedre, vagy tedd a public_html-en KÍVÜLRE (eggyel feljebb, pl. backup-regi-oldal).
  2. Ürítsd ki a public_html-t. Ha csak fölé másolsz, a régi fájlok egy része ott ragad (régi aloldalak, régi CSS és képek).
  3. Töltsd fel az újat a 4.1 szerint.
⚠️ A mentés NE a public_html-ben maradjon! Egy public_html/regi-oldal/ mappa az interneten is elérhető lenne (kemence-akademia.xyz/regi-oldal/), és a Google is indexelhetné.

A megszűnő aloldalak átirányítása. A régi oldal három aloldala az új rendszerben nem létezik, ezért 404-et adna. A web/.htaccess ezt már tartalmazza:

Redirect 301 /pizza-akademia.html  /
Redirect 301 /burek-akademia.html  /
Redirect 301 /kenyer-akademia.html /

Ugyanez kattintgatva is beállítható: hPanel → a weboldal → Advanced → Redirects. Mielőtt kiürítenéd a public_html-t, nézd végig a fájllistát — ha több régi .html van, vedd fel azokat is.

4.3 — Átállás a Minupról

A régi oldalon a foglalás nem is ott történt: a főoldalon egy Minup-naptár volt beágyazva (app.minup.io/embed/kemence-akademia/events), az aloldalakon pedig egy gomb a app.minup.io/book/kemence-akademia címre. Ezt váltja ki az új rendszer, ezért a váltásnak van négy teendője:

  1. Élő foglalások átemelése. A Minupban maradt jövőbeli foglalásokról az új rendszer nem tud (nincs bennük a naptárban, nem kapnak emlékeztetőt). Az adminban nincs kézi foglalásfelvétel, ezért SQL-lel kell betölteni őket: db/t_minup-import.sql. Előbb vidd fel az adminban a programokat és az alkalmakat ugyanazokkal a dátumokkal, csak utána futtasd. A script két menetben dolgozik (előbb ellenőriz, aztán tölt), és a betöltés nem küld levelet a régi vendégeknek.
  2. Külső linkek átírása. Amik nem a mi domainünkön vannak, azokat a .htaccess nem tudja átirányítani: Google Cégprofil („Időpontfoglalás" gomb), Facebook-oldal gombja és posztok, korábbi hirdetések, e-mail aláírás.
  3. A Minup-oldal kikapcsolása. A app.minup.io/book/kemence-akademia a váltás után is élne, és aki odatéved, egy már nem figyelt rendszerbe foglalna. Kapcsold ki az eseményeket, vagy írd ki, hogy az új oldalon lehet foglalni.
  4. Előfizetés lemondása a Minupnál, ha fizetős — ez valódi megtakarítás az ügyfélnek.

4.4 — Domain / DNS

A kemence-akademia.xyz domain a Hostingeren van. Amikor a 4.1-ben hozzáadod a website-ot, a Hostinger jellemzően magától a saját szerverére állítja az A-rekordot. Ha nem: a DNS Zone Editor-ban az A rekord (@) a Hostinger tárhely IP-jére mutasson. Az e-mail (Resend) send. rekordjait (2.2) ne bántsd.

4.5 — Demó a Cloudflare-en (az élestől külön)

A bemutató verzió a Cloudflare-en fut, a kemence-demo GitHub-repóból (farjan86/kemence-demo), automatikus telepítéssel: ami felkerül a repóba, az pár perc múlva élesedik a demó címén. Ez az éles telepítést nem érinti.

Frissítés a fejlesztői projektből: a kemence-demo mappában a frissit-es-commit.bat átmásolja a web/ tartalmát (a config.js kivételével, hogy a demó a saját Supabase-projektjén maradjon), majd commitol és pushol.

A demó és az éles KÜLÖN Supabase-projekt. A demóban nyugodtan lehet próbafoglalás; az éles adatok közé nem keveredik. A két config.js ezért soha nem cserélődhet fel.

(Korábban volt egy Netlify-os demó is — az a projekt törölve lett.)

5. Keep-alive (a Supabase ne aludjon el)

Az ingyenes Supabase projekt ~7 nap inaktivitás után szünetel. Egy periodikus, kívülről érkező API-kérés aktivitásnak számít, és nullázza az inaktivitás-számlálót. Már az oldal megnyitása is aktivitás (a főoldal betölti a programokat + a látogatás-számlálót a Supabase-ből), tehát rendszeres forgalomnál gyakran nem is aludna el, de alacsony forgalmú / szezonális oldalnál kell a biztosíték.

Két út: fejlesztéshez a repóban lévő GitHub Actions (5.1); élesben a cron-job.org (5.2), mert az nem függ a fejlesztő GitHub-jától (és a kliensnek nincs is GitHub-ja).

5.1 — Dev / demó: GitHub Actions (2 secret)

  1. GitHub → a repo → Settings → Secrets and variables → Actions → New repository secret, vegyél fel kettőt:
Secret neveÉrték
SUPABASE_URLhttps://<PROJECT_REF>.supabase.co (a config.js SUPABASE_URL-je)
SUPABASE_ANON_KEYaz anon public kulcs (publikus, RLS védi)

Teszt: GitHub → Actions fül → Supabase keep-alive → Run workflow. Zöld pipa = működik.

Két korlát:
  • A GitHub letiltja az ütemezett workflow-t 60 nap repó-inaktivitás után (ha nincs commit). Aktív fejlesztésnél nem gond; bármelyik commit újraaktiválja. Teljesen „magára hagyott" éles repónál buktató lehet.
  • Fizetős Supabase-csomagon a projekt nem alszik el — akkor a keep-alive fölösleges.

5.2 — Éles / kliens: cron-job.org (ingyenes, GitHub nélkül) — AJÁNLOTT

Élesben a keep-alive NE a fejlesztő GitHub-jától függjön (a kliensnek nincs is GitHub-ja). Erre a legjobb ingyenes megoldás a cron-job.org: a felhőben fut 24/7, nem függ egyetlen géptől/telefontól sem, és a fiók a kliensé lehet (átadható). Tud egyedi fejlécet küldeni (kell az anon kulcs), így tiszta 200-as választ kapunk.

  1. Regisztrálj: cron-job.org (ingyenes). Élesnél érdemes a kliens / csapat e-mailjével, hogy az övé legyen.
  2. Create cronjob → töltsd ki:
MezőÉrték

URLhttps://<PROJECT_REF>.supabase.co/rest/v1/workshops?select=id&limit=1
ScheduleEvery day at 8:00 (a napi futás a legegyszerűbb és bőven elég; csak 7 napnál sűrűbb kell). Ne bajlódj a „2 naponta"-val.

Request headers (a beállításban „Advanced" / „Headers") — ez a fontos, e nélkül 401 jönne:

Mentés → a cronjob legyen Enabled. A cron-job.org rögtön kipróbálja; a History/Log alatt HTTP 200 = működik. (Kézzel is: „Run now" / „Test run".)

„Zéró gondos" alternatíva: fizetős Supabase (Pro, ~$25/hó) — a projekt soha nem alszik el, nincs keep-alive, nincs karbantartás. Valódi, bevételt termelő rendszernél ez a legtisztább; az ügyfél döntése/költsége.
Miért a workshops végpontot pingeljük? Ez a Supabase auto-generált REST API-ja (PostgREST): a workshops táblából kér le egy apró adatot (select=id&limit=1 = csak egy sor egyetlen mezője). Publikusan olvasható (RLS engedi), a válasz pici, és a kérés átmegy a Supabase API-átjáróján → ez számít aktivitásnak. Bármelyik létező, anon-olvasható tábla/nézet megtenné.
